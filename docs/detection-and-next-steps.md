# 관제 검증과 후속 과제

## 관제에서 연결한 신호

| 관찰 대상 | 확인하려는 신호 | 분석 목적 |
| :--- | :--- | :--- |
| 웹·애플리케이션 | 요청 경로, 응답 상태, WAF 이벤트, 인증 결과 | 취약점 탐색과 악용 시도 구분 |
| 메일·첨부파일 | SMTP 처리 흐름, 악성 파일 검사 결과 | 의심 파일 유입과 전달 경로 확인 |
| 호스트·계정 | 로그인, 프로세스, 파일 변경 및 시스템 이벤트 | 계정 악용과 호스트 변경 추적 |
| 네트워크·운영 | 연결, 방화벽·IDS 이벤트, CPU·메모리·트래픽 | 공격 징후와 서비스 장애를 함께 판단 |

## 보고서에서 확인한 한계

- 통합 사이트는 여러 관제 서비스에 접근하게 하지만, 탐지 결과를 공통 사건으로 자동 합치는 기능은 추가 구현이 필요합니다.
- 중앙 로그 전송에는 큐와 재시도가 있으나, 최종 저장까지 보장하는 확인 절차는 보완이 필요합니다.
- 비표준 로그의 파서와 호스트 간 연관분석 범위는 확대해야 합니다.
- 자원 사용량 급증만으로 공격을 확정할 수 없어 서비스·방화벽·호스트 로그를 함께 대조해야 합니다.
- 자동 차단·격리, 승인 흐름, 대응 이력과 복구 훈련은 향후 과제입니다.

## 다음 단계

1. 관제 제품의 탐지 결과를 공통 사건 모델로 묶고 근거 로그를 연결합니다.
2. 로그 수집부터 저장까지 전달 상태를 확인하고 실패를 가시화합니다.
3. 실증된 공격 시나리오와 탐지 규칙을 연결해 오탐·미탐을 반복 점검합니다.
4. 대응 자동화에는 승인, 실행 기록 및 복구 절차를 함께 설계합니다.
